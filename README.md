# 智能家居指令失败：先处理过期心跳

## 我的判断

**优先干预的是下发时心跳已过期的指令。** 发放数据共 1021 行，49 行是完全重复的 `command_id` 记录。去重后有 972 条唯一指令，其中成功 840 条、超时或未响应 98 条、状态未回传 34 条。只在结果已知的 938 条中计算，失败率为 **98/938 = 10.45%**。未知状态没有并入成功或失败。

用带时区的 `dispatched_at - last_heartbeat_at` 计算心跳间隔。全量唯一指令中，间隔 **≥15 分钟**的 233 条有 220 条结果已知，其中 **82/220 = 37.27%** 失败；间隔 **<15 分钟**的 739 条有 718 条结果已知，其中 **16/718 = 2.23%** 失败。前者包含了 **82/98 = 83.67%** 的已知失败。相较之下，`signal_strength <10` 与 `≥10` 两组的失败率分别是 **39/320 = 12.19%** 和 **59/618 = 9.55%**；信号数值的单位及方向未提供，不宜据此做无线覆盖结论。

**根问题假设：**网关在沿用较久未更新的设备在线状态时仍直接下发，缺少基于心跳新鲜度的探活与失败后的明确反馈。这里的数据只能证明“旧心跳与失败高度相关”，不能证明旧心跳导致失败，也没有记录现行网关是否已经探活。尤其不能把题目描述的“夜间哑火”当成本数据已验证的事实：这份数据覆盖 2026-09-01 至 09-07，但本地小时只有 **07:00–21:59**，22:00–06:59 的记录为 **0**。

## 做了什么

实现了前置规则和后续处理闭环：**心跳间隔 ≥15 分钟先探活；在线则下发，离线则保留指令并通知住户，设备恢复后在有效期内再尝试。** [`policy.py`](policy.py) 处理带时区时间戳及边界；[`intervention.py`](intervention.py) 实现实际流程的网关适配接口与可执行编排，调用探活、下发、状态核查、通知和升级处理。只有规则命中仍不算干预，改变下发与失败后的处理才可能减少住户打扰。

闭环的关键分支：探活失败时**不丢弃用户意图**，暂存指令，恢复后重试；等待超时则明确告知未执行并升级处理。下发后没有回执时先核查设备是否已达到目标状态；若已达到则不重复执行，若确认未达到且该指令可安全重试，最多再发一次；状态无法确认或不适合重试时，通知住户并升级处理。相同 `command_id` 不会因再次提交而重复发送。测试使用标明为模拟的网关输入，只验证流程行为，**不用于任何业务效果结论**。

这是一份**可执行的参考实现，不是已接入生产网关的成品**：`Gateway` 接口需要真实设备协议适配，内存待执行队列需要替换为持久队列并保证重启后的去重，是否可安全重试也必须由设备命令语义给出。现有 CSV 缺设备 ID、目标状态、探活和住户反馈，不能回放这套闭环的真实收益。

阈值只用 9 月 1–5 日数据从 5、10、15、20、30、45、60 分钟候选中选取：按题给的 90 分钟/失败与 12 分钟/探活，最大化“若被标记的失败全部可避免”的**乐观净节省上限**。15 分钟在训练段为 3258 分钟，高于 20 分钟的 3000 分钟。9 月 6–7 日完全留作时间外验证，未参与选阈值。

| 9 月 6–7 日留出集 | 唯一指令 | 结果已知 | 已知失败 | 已知失败率 |
| --- | ---: | ---: | ---: | ---: |
| 心跳间隔 ≥15 分钟，先探活 | 62 | 59 | 23 | 38.98% |
| 心跳间隔 <15 分钟，照常下发 | 206 | 203 | 3 | 1.48% |

留出集 26 条已知失败中，规则识别出 **23 条（88.46%）**。这验证了*风险分层在后两天仍存在*，并不验证探活会防止失败。`execution_status=0` 包括超时与未响应，也不等同于每次都是题给的“设备失联失败”。

## 怎么证明有用

先用留出集作**条件性经济核算**，再建议上线实验。探活 62 次的题给成本为 **62×12 = 744 分钟**。若其中 23 条已知失败全部属于可避免的失联失败，最大可挽回 **23×90 = 2070 分钟**，乐观净值为 **1326 分钟**。因此，实际至少需避免 **9/23 条**被标记的已知失败（`ceil(744/90)=9`），才可覆盖探活成本；所需有效避免比例为 **35.94%**。这些是条件推算，**不是已实现的节省**。对留出集全部 268 条指令一律探活，即便把 26 条已知失败全避免，上限仍是 `26×90−268×12 = −876` 分钟，故优先验证定向探活。

上线前做随机对照：只对规则命中的指令，在相同设备/住户维度随机分流“现有流程”和“探活、暂存、恢复重试、反馈闭环”，记录设备 ID、场景 ID、探活结果、最终执行、住户手动重试、投诉和额外等待。主要指标是每 100 条指令的住户可感知失败与总打扰分钟，护栏是 P95 执行延迟、未回传比例和额外网关负载。若真实减少的打扰不足以抵消探活成本，或延迟恶化，则停止推广；否则逐步扩大。现有 CSV 没有设备 ID、夜间记录、探活结果和重试链路，不能从本表估计因果收益。

## 复现

本分析只使用题目发放的 `device_commands.csv`，没有补造数据。原始记录含设备所属房间与精确时间，公开仓库不附带 CSV；请从任务页面下载原文件，放在仓库根目录，保持文件名不变。Python 3.9+ 标准库即可：

```bash
python analyze.py
python -m unittest discover -p "test_*.py" -v
```

`analyze.py` 将同一 `command_id` 的完全重复行去掉；若同 ID 内容冲突则直接报错。它验证字段和状态值、按时区计算心跳间隔、以最后两天做留出集，并在本地生成 `results.json`。所有上文数字都能在该 JSON 的 `overall`、`all`、`train`、`holdout`、`candidate_train_results` 中核对。`test_policy.py` 检查时间与阈值；`test_intervention.py` 用模拟网关验证离线暂存、恢复执行、未知回执不盲目重试、确认未执行时限次重试、过期升级。

## 判断与限制

- `execution_status` 空值为“未回传”，是单独的数据质量问题；需要追踪回执链路。当前 34 条未知状态未用于失败率分母，但命中规则时计入探活工作量。
- 数据没有单独的设备标识。`command_id` 是指令流水，不可拿来识别反复掉线的设备。
- 90 与 12 分钟来自题目口径。90 分钟只有在确属设备失联失败时适用；实际可避免比例未知。
- 时间外留出集只有两天，且没有夜间样本。阈值需要经真实夜间数据和在线实验复核。
